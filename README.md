# 天凤牌山生成算法与随机分布验证

本文分析天凤公开的牌山算法，并使用官方中间值和对应牌谱进行本地复现，分别讨论四麻的 136 张牌和三麻的 108 张牌。

```bash
python3 verify_tenhou_shuffle.py                 # 复现本文全部检查（只用标准库，离线）
python3 tenhou_shuffle.py replay LOG.xml         # 用种子核对任意天凤牌谱
python3 tenhou_shuffle.py commit LOG.xml --list before.txt   # 核对事前哈希承诺
```

详细用法见[第 9 节](#9-文件与复现方法)。

## 1. 结论与验证范围

天凤公开的方案是由随机种子驱动的伪随机洗牌，核心是 **MT19937 → SHA-512 → Fisher–Yates**。在洗牌整数可以视为独立均匀随机数的假设下，它产生非常接近均匀分布的牌山；由于直接取余，严格数学意义上不是完全均匀。

本次成功复现了官方示例的全部中间值和完整四麻牌山，并与对应牌谱中的配牌、骰子、初始宝牌指示牌和全部 64 次摸牌逐项对齐。在此基础上，又用 2012 年和 2026 年 11 月的四麻、三麻凤凰桌牌谱核对了多小局、杠、拔北、岭上牌、杠宝牌和里宝牌，所有记录的牌都与种子生成的牌山一致。

但这还不足以单独证明所有实际对局都按未经筛选的随机种子运行。对此，天凤另外提供了对局前公布种子哈希、对局后核验的机制。本次还原了该哈希的序列化格式，用天凤 CGI 的输出确认了格式，并对三场三麻凤凰桌对局完成了一次严格的事前核验：在对局开始前保存列表，事后在本地计算哈希并在列表中找到（第 7 节）。**这只是一次小样本核验；本次没有审计服务器内部的种子来源。**

| 要判断的问题 | 本次可以得出的结论 |
| :---: | :---: |
| 是否存在公开的、可以复现牌山的算法 | 是，官方算法与官方示例均可访问 |
| 本地能否从种子复现官方示例 | 能，全部中间值、完整牌山及牌谱检查均通过 |
| 当前实际对局是否仍使用同一算法 | 2026-11-02 下载的凤凰桌四麻、三麻牌谱全部吻合 |
| 种子哈希承诺的格式是否可独立复现 | 能，见第 7.1 节 |
| 实际对局的种子是否事前已承诺 | 抽查的 3 场三麻对局是，见第 7.3 节 |
| 理想随机整数输入下是否严格均匀 | 否，直接取余产生微小偏差 |
| 理想随机整数输入下是否近似均匀 | 是，取余造成的概率相对偏差至多约百万分之一 |
| 是否已证明当前服务器的全部牌山都随机 | 没有；公开算法、历史样例和实际运行是不同层次的证据 |
| 是否发现公开洗牌逻辑按账号、点数或牌型调整牌山 | 没有；公开的洗牌过程不以这些变量为输入 |

官方手册说明牌山与王牌在开始前排列，再按顺序消耗，并将 2009 年 7 月 22 日以后的生成方式指向本文核查的算法。算法文章发表于 2009 年 7 月 13 日，仍带有样例和计划性质的说明；2016 年官方验证向量及对应牌谱进一步提供了实际可复现的证据。因此，本文核验的是这套公开算法及该历史样例，不把文章中的旧版系统 API 当作当前服务器配置的证明。[天凤手册](https://tenhou.net/man/)、[算法公开说明](http://blog.tenhou.net/article/30503297.html)、[官方验证数据](http://blog.tenhou.net/article/174202532.html)。

## 2. 随机牌山的数学含义

先把每张实体牌赋予独立编号，即使两张牌的牌面相同，也视为不同实体。四麻有 $`n=136`$ 张，三麻有 $`n=108`$ 张。

理想均匀牌山要求每个排列 $`\pi`$ 的概率相同：

```math
P(\Pi=\pi)=\frac{1}{n!}.
```

如果从牌山的固定 14 个位置取得庄家起手牌，每个实体牌的 14 张子集就应具有相同概率：

```math
P(H)=\frac{14!(n-14)!}{n!}=\frac{1}{\binom{n}{14}}.
```

对牌面计数为 $`c_1,\ldots,c_t`$ 的手牌，每种牌有 4 张，则：

```math
P(c_1,\ldots,c_t)
=\frac{\prod_{a=1}^{t}\binom{4}{c_a}}{\binom{n}{14}},
\qquad \sum_{a=1}^{t}c_a=14.
```

这正是理论天和概率等组合计数使用的抽样模型。牌山的读取方向、固定发牌位置、红牌的固定实体编号，只改变位置或标签，不会破坏理想均匀排列的性质。

“算法可复现”与“抽样均匀”可以同时成立：随机种子决定一张牌山，种子公开后牌山当然可以重建；概率来自种子在生成前的不确定性。

## 3. 公开算法的流程

### 3.1 种子与对局状态

官方样例先调用 Windows 的 `CryptGenRandom` 取得根种子，初始化根 MT19937；再由根生成器分配每场对局的种子。每场对局用自己的 MT19937 连续生成各小局的牌山。

牌谱中的版本标识为 `mt19937ar-sha512-n288-base64`。其 Base64 部分解码为 2496 字节，即 624 个小端序的 32 位整数：

```math
624\times32=19968\text{ 位输入种子数据}.
```

这不表示种子有 19968 位已经证明的独立熵，也不表示 MT 内部状态的有效位数等于输入长度。实际熵取决于根种子的产生与后续映射。

### 3.2 每小局生成洗牌整数

每小局从对局 MT 状态中连续取得 288 个 32 位整数，拆成 9 组，每组 32 个：

```math
9\times32\times32=9216\text{ 位}.
```

每组以小端序序列化为 128 字节，计算 SHA-512，得到 64 字节，再按小端序解析为 16 个 32 位整数。最终拼接得到：

```math
9\times16=144\text{ 个洗牌整数}.
```

哈希把每组 1024 位压缩为 512 位。它不是额外的随机源，不能凭空增加熵；其作用是混合 MT 输出。将哈希结果视为理想独立均匀整数，是后文偏差分析的建模假设，而不是 SHA-512 已被数学证明具有的分布结论。

### 3.3 Fisher–Yates 洗牌

先令实体牌按编号排列，然后依次交换：

```python
wall = list(range(n))
for i in range(n - 1):
    j = i + rnd[i] % (n - i)
    wall[i], wall[j] = wall[j], wall[i]
```

四麻进行 135 次交换，三麻进行 107 次。三麻对 108 个序号洗牌，再把序号依次映射到去掉二万至八万（实体编号 4–31）后剩下的 108 个实体编号；这一映射由实际三麻牌谱确认。两种规则都使用 `rnd[135] % 6` 和 `rnd[136] % 6` 生成两枚零起算骰子。

公开过程在对局进行前决定整座牌山；后续固定顺序读取牌山，与根据局面重新挑选下一张牌有本质不同。但能否排除事前挑选整场种子，需要结合第 7 节的核验机制。

## 4. 为什么理想 Fisher–Yates 均匀

第 $`i`$ 步的剩余候选数为 $`m=n-i`$。如果每步在 $`m`$ 个位置中独立等概率选择，则任何特定交换选择序列的概率为：

```math
\prod_{m=2}^{n}\frac1m=\frac1{n!}.
```

每个最终排列恰好对应一条选择序列，因此所有排列等概率。这个证明要求的是各步选择在给定此前选择后仍均匀；仅有每个整数单独看来均匀，并不够。

天凤采用的交换结构符合这一算法。需要量化的差异是：它用有限范围整数取余，代替了严格均匀的 $`m`$ 选一。

## 5. 直接取余的偏差

### 5.1 单步概率

设 $`U`$ 在 $`0,1,\ldots,M-1`$ 中均匀分布，其中 $`M=2^{32}`$。写成：

```math
M=qm+r,\qquad 0\le r\lt m.
```

令 $`J=U\bmod m`$。前 $`r`$ 个余数分别有 $`q+1`$ 个原像，其余 $`m-r`$ 个余数分别有 $`q`$ 个原像，因此：

```math
P(J=j)=
\begin{cases}
\dfrac{q+1}{M},&0\le j\lt r,\cr
\dfrac qM,&r\le j\lt m.
\end{cases}
```

当且仅当 $`r=0`$ 时，该步严格均匀。由于 $`2^{32}`$ 的因子只有 2 的幂，候选数为 3、5、6 等时都会出现取余偏差。

例如首步四麻有 $`m=136`$，此时：

```math
2^{32}=136\times31580641+120.
```

因此 120 个余数各有 31580642 个原像，另外 16 个各有 31580641 个原像。

每个余数相对理想概率的绝对差为：

```math
P(J=j)-\frac1m=
\begin{cases}
\dfrac{m-r}{mM},&j\lt r,\cr
-\dfrac r{mM},&j\ge r.
\end{cases}
```

其绝对值小于 $`1/2^{32}`$。官方样例的交换语句也明确注明接受这一精度的误差。

### 5.2 整座牌山的总变差上界

总变差距离衡量任意事件的概率最多相差多少。单步取余分布与均匀分布之间的总变差为：

```math
\delta_m
=\frac12\sum_{j=0}^{m-1}\left|P(J=j)-\frac1m\right|
=\frac{r(m-r)}{mM}.
```

在各步 32 位输入独立均匀的模型下，可以逐步耦合两种洗牌过程，从而得到：

```math
d_{\mathrm{TV}}(P_n,Q_n)
\le\sum_{m=2}^{n}\delta_m.
```

其中 $`P_n`$ 是带取余偏差的牌山分布，$`Q_n`$ 是理想均匀牌山分布。

| 场景 | 交换次数 | 整座牌山总变差上界 |
| :---: | :---: | :---: |
| 四麻，136 张 | 135 | $`3.227355422805873\times10^{-7}`$ |
| 三麻，108 张 | 107 | $`2.203658750325221\times10^{-7}`$ |

这些数值只约束取余这一环节，不包括种子分布、MT 输出相关性或哈希输出与理想模型的差异。

### 5.3 对天和等稀有事件更有用的相对上界

总变差给出绝对误差，直接除以稀有事件概率往往得到过于宽松的结论。可以改为约束每个排列的概率比。

当 $`r_m=M\bmod m\gt 0`$ 时，单步实际概率除以理想概率，只有两种取值：

```math
\frac{P(J=j)}{1/m}
\in\left\{1-\frac{r_m}{M},\;1+\frac{m-r_m}{M}\right\}.
```

当 $`r_m=0`$ 时，该比值恒为 1。令 $`I_n=\{m:2\le m\le n,\ r_m\gt 0\}`$，则每个排列都满足：

```math
L_n\le\frac{P_n(\pi)}{Q_n(\pi)}\le H_n,
```

其中：

```math
L_n=\prod_{m\in I_n}\left(1-\frac{r_m}{M}\right),
\qquad
H_n=\prod_{m\in I_n}\left(1+\frac{m-r_m}{M}\right).
```

对事件 $`A`$ 的所有排列求和，仍有：

```math
L_n\le\frac{P_n(A)}{Q_n(A)}\le H_n,
\qquad Q_n(A)\gt 0.
```

因此，**在同一独立均匀整数模型下，这个上界同样适用于天和，而不只适用于常见事件**。

| 场景 | 最大相对降低上界 $`1-L_n`$ | 最大相对增加上界 $`H_n-1`$ |
| :---: | :---: | :---: |
| 四麻 | $`9.494829207262027\times10^{-7}`$ | $`1.160195761315065\times10^{-6}`$ |
| 三麻 | $`6.307380182596622\times10^{-7}`$ | $`7.101337111874817\times10^{-7}`$ |

四麻最大相对增加约为 **0.00011602%**，三麻约为 **0.00007101%**。所以，仅取余操作本身不能解释百分比级的天和频率偏离。这一结论不等于已经给整个真实生成链条建立了相同的误差上界。

## 6. 伪随机数与严格均匀的边界

MT19937 是确定性的伪随机数生成器，不是密码学安全随机数生成器。相同初始状态会产生相同输出。SHA-512 的参与也不能把“确定性的输出序列”变成数学上的独立真随机序列。

因此，不能把第 5 节在独立均匀整数模型下的偏差界，直接宣称为真实 MT19937 → SHA-512 整条链的无条件定理。当前证据支持的是：算法结构合理、可复现，通常可以按高质量伪随机洗牌使用；完整随机性仍依赖种子质量和生成链的统计、密码学性质。

严格均匀的要求甚至比一般伪随机系统能够保证的性质更强。假设一个确定性生成器接收均匀的固定 $`b`$ 位种子，则每个输出概率都是 $`k/2^b`$。若要让 $`n!`$ 个排列严格等概率，就必须有：

```math
\frac{k}{2^b}=\frac1{n!},\qquad n!\mid2^b.
```

当 $`n\ge3`$ 时，$`n!`$ 含有因子 3，这不可能成立。这说明固定长度二进制种子驱动的确定性洗牌通常也无法达到所有排列严格等概率；它本身并不是人为操纵的证据。

若只想消除取余偏差，可以使用拒绝采样：令 $`T=M-(M\bmod m)`$，反复抽取 $`U`$，仅在 $`U\lt T`$ 时返回 $`U\bmod m`$。此时每个余数恰好有 $`T/m`$ 个原像。不过，这只是可行的算法改进，不是本次核查到的天凤公开实现。

## 7. 事前哈希承诺解决什么问题

[天凤的种子哈希公开页面](https://tenhou.net/stat/rand/)说明，种子在登录、预约及对局开始之前已经决定，并通过 SHA-512 列表提供事前核验入口。页面给出的严格流程是：在预约前保存相应规则的哈希列表；对局结束后，从牌谱及座位信息重新计算哈希，再检查它是否位于事前列表的适当位置。原文还指出，使用天凤自己的 CGI 代算不能算严格的独立验证。

这比仅公开牌谱种子多了一层约束。仅有种子和牌谱一致，仍可能是先筛选到喜欢的牌山，再公布对应种子；事前承诺则使运营方事后替换已承诺的数据非常困难。

但必须区分以下事项：

| 机制或检查 | 能支持的判断 | 尚不能单独支持的判断 |
| :---: | :---: | :---: |
| 种子能复现牌谱 | 已观察对局与该种子及算法一致 | 种子产生前没有筛选 |
| 哈希在对局前已公布且事后匹配 | 匹配的数据在承诺后未被替换，依赖哈希安全性 | 承诺前的种子一定来自均匀随机源 |
| 消费顺序与独立留存列表吻合 | 受检对局没有跳过列表中的既定顺序 | 所有时间、所有房间都同样执行 |
| 大样本统计接近理论 | 受检统计量没有显示相应异常 | 所有高阶牌型和相关性都已验证 |

官方说明也列出了生成服务器维护时无法验证、部分高负载场合列表位置可能偏移，以及不面向个室、大赛和测试对局公开等限制。

### 7.1 哈希输入的格式

官方页面只给出长度：$`4+624\times8=4996`$ 字节，其中 4 字节是“座位排列信息”，$`624\times8`$ 字节是种子。页面没有说明具体编码，也没有给出测试向量。

本次向天凤的 `verify.cgi` 提交了 13 份牌谱，取得官方计算的哈希，再在本地枚举候选编码。唯一吻合的格式是：

```text
SHA512( 座位排列的 4 个 ASCII 数字 + 2496 字节原始种子的小写十六进制 )
```

例如官方 2016 年样例的输入以 `3120` 开头，后接 4992 个十六进制字符。13 份牌谱都只有一种座位排列能得到官方哈希。其中 5 份作为测试向量保存在 `commitment_vectors.json`。

座位排列不记录在牌谱中，对局者看到的座位与它的关系也未公开；`verify.cgi` 的结果与 URL 中的 `tw` 参数无关。因此本地实现对 24 种排列分别计算哈希，然后在列表中查找。这会让单份列表的误匹配概率乘以 24，对 SHA-512 而言仍然可以忽略。

`verify.cgi` 只用来确定格式。按官方说明，用天凤自己的 CGI 计算哈希不算严格的独立验证；本仓库的 `commit` 命令完全在本地计算。

### 7.2 本地核验工具

```bash
# 1. 预约对局前保存当前规则的列表，例如凤凰南喰赤（00000-00a9）
curl -o before.txt 'https://tenhou.net/stat/rand/?00000-00a9'
# 2. 对局结束后下载牌谱，在保存的列表中查找
python3 tenhou_shuffle.py commit LOG.xml --list before.txt
```

规则代码就是列表页面链接中 `?` 之后的部分。找到时输出条目位置、是否已标为 `USED` 以及匹配的座位排列；找不到时退出码为 1。

列表每行固定 128 个字符。条目被消耗后，行首的 ` USED ` 会覆盖哈希的前 6 个十六进制字符，只剩后 122 个；工具按后缀匹配这种条目。已消耗的条目在之后几次刷新中会从列表中消失，所以列表需要在对局开始前保存，不能事后补抓。

严格核验要求两点：保存列表的时间早于对局开始，并且匹配到的条目在保存时还没有标为 `USED`。

这次核验的范围有限：

- 只有一种规则、一份列表、三场对局，时间跨度约 6 分钟；四麻在这段时间没有完成严格核验。
- 我们不是这三场的对局者。核验说明这些种子在对局开始前已经确定，但无法说明种子分配给对局时是否与玩家有关。
- 只能说明承诺之后种子没有被替换，不能说明承诺之前种子是如何产生的（见第 7 节开头的表格）。

## 8. 本次实际执行的验证

### 8.1 官方 2016 年样例

使用官方 2016 年示例 `2016022509gm-0009-0000-b327da61`。将官方页面中的数据提取为本地固定向量，重新实现 MT19937、字节序、SHA-512 分块和交换过程，并下载对应原始牌谱进行核对。脚本每次运行时还会从缓存的官方网页重新解析这些数组，确认固定向量与网页一致。

| 检查项目 | 规模 | 结果 |
| :---: | :---: | :---: |
| Base64 解码与官方 `init` 数组 | 624 个整数 | 全部一致 |
| MT19937 输出与官方 `src` 数组 | 288 个整数 | 全部一致 |
| SHA-512 输出与官方 `rnd` 数组 | 144 个整数 | 全部一致 |
| 四麻完整 `yama` 数组 | 136 张实体牌 | 全部一致 |
| 牌谱中的种子 | 完整种子 | 与官方示例一致 |
| 四家配牌 | 每家 13 张，合计 52 张 | 内容及记录顺序全部一致 |
| 骰子 | 2 个零起算值 | 全部一致 |
| 初始宝牌指示牌 | 1 张 | 一致 |
| 牌谱中的普通摸牌 | 全部 64 次 | 全部一致 |

四麻原始数组从高索引向低索引发牌。每家按三轮各 4 张、再各 1 张取得 13 张配牌，随后庄家的第一次摸牌单独记录。因此本次不是把配牌任意排序后只比牌面，而是核对实体编号与记录顺序。

### 8.2 通用牌谱核对

`tenhou_shuffle.py replay` 对任意 `mt19937ar-sha512-n288-base64` 牌谱逐小局核对。各小局依次从同一个对局 MT 状态取 288 个整数。牌山位置如下，`yama` 指 Fisher–Yates 输出数组，发牌从数组末尾开始：

| 项目 | 四麻 | 三麻 |
| :---: | :---: | :---: |
| 配牌 | 每轮 4 家 × 4 张，共 3 轮，再各 1 张 | 每轮 3 家 × 4 张，共 3 轮，再各 1 张 |
| 普通摸牌 | 配牌后顺序向 `yama` 低索引方向 | 同左 |
| 岭上牌（杠、加杠、拔北） | `yama[1], [0], [3], [2]` | `yama[1], [0], [3], [2], [5], [4], [7], [6]` |
| 宝牌指示牌 | `yama[5], [7], [9], ...` | `yama[9], [11], [13], ...` |
| 里宝牌指示牌 | `yama[4], [6], [8], ...` | `yama[8], [10], [12], ...` |
| 三麻实体编号 | 不适用 | 序号 $`k`$ 映射为去掉 4–31 后的第 $`k`$ 个编号 |

官方文章只公开了洗牌本身；上表中发牌、岭上牌和宝牌的位置是根据牌谱推出的，再用下列牌谱逐张核对：

| 牌谱 | 规则 | 小局 | 覆盖 |
| :---: | :---: | :---: | :---: |
| `2016022509gm-0009-0000-b327da61` | 四麻 | 1 | 官方样例，吃 |
| `2012062106gm-00c1-0000-8b0f7563` | 四麻 | 2 | 多小局、庄家轮换、里宝牌 |
| `2026110210gm-00a9-0000-36442307` | 四麻凤凰 | 11 | 加杠 |
| `2026110210gm-00a9-0000-7d730942` | 四麻凤凰 | 12 | 暗杠或大明杠、杠宝牌 |
| `2026110210gm-00b9-0000-1e1dadd7` | 三麻凤凰 | 9 | 拔北、杠、加杠、24 次岭上摸牌 |

这 5 份牌谱随仓库附带并由 `verify_tenhou_shuffle.py` 检查。第 7.3 节的 3 份三麻牌谱也随仓库附带并经过同样的核对。开发时另外核对了 2026-11-02 当天下载的全部 72 份凤凰桌牌谱（41 份四麻、31 份三麻，共 732 小局）：34125 张配牌、29407 次普通摸牌、777 次岭上摸牌、1452 张宝牌指示牌和 310 张里宝牌指示牌全部一致。其余牌谱没有附带进仓库。

仍未覆盖：四开杠、九种九牌等特殊流局后的规则细节，以及 2009 年前旧算法的牌谱。脚本只核对牌谱中出现的牌，不推断未公开的牌。

## 9. 文件与复现方法

需要 Python 3.9 或更高版本，只用标准库，不需要联网，不会生成结果文件：

```bash
python3 verify_tenhou_shuffle.py         # 复现本文全部检查与数值
python3 -m unittest discover -s tests    # 单元测试
```

核对自己的牌谱：

```bash
curl -o LOG.xml 'https://tenhou.net/0/log/?2026110210gm-00a9-0000-7d730942'
python3 tenhou_shuffle.py replay LOG.xml   # 核对配牌、摸牌、岭上牌、宝牌
python3 tenhou_shuffle.py hash LOG.xml     # 输出 24 种座位排列下的承诺哈希
```

`replay` 也接受 gzip 压缩的牌谱。

| 文件 | 用途 |
| :---: | :---: |
| `tenhou_shuffle.py` | 洗牌实现、通用牌谱核对、种子哈希承诺计算与命令行入口 |
| `verify_tenhou_shuffle.py` | 复现本文：校验来源缓存、核对官方向量与牌谱、精确计算取余偏差上界 |
| `tests/` | 单元测试，包括 MT19937 参考输出和篡改牌谱的检测 |
| `official_test_vector.json` | 从官方验证页面提取的种子和全部中间值 |
| `commitment_vectors.json` | `verify.cgi` 给出的承诺哈希，用作序列化格式的测试向量 |
| `sources/` | 官方页面、MT19937 参考 C 源码与牌谱的原始缓存，原网页编码保持不变 |
| `sources/manifest.json` | 来源地址、获取日期、文件字节数及 SHA-256 |
